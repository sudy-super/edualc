## 実行中の会話でauthentication_failedになる問題

- [x] 直通のAPIキー認証・実ログ・稼働SDKとLiteLLMのヘッダー転送を確認する。
- [x] 別の起動が共有runtime-auth.jsonを書き換える条件を再現する。
- [x] 起動時の認証を固定し、接続経路のヘッダーを共有ファイルから分離する。
- [x] 模擬APIと導入版で、並行起動後も専用キーが届くことと認証分離を検証する。

### 方針

- runtime-authにはedualc専用の認証だけを保存し、LiteLLMの接続ヘッダーは各起動の環境からSDKへ渡す。
- SDK接続側では起動時に認証を読み取り、後から同じファイルが変わっても実行中の会話へ反映しない。
- 専用キーがない場合に本家のOAuthや別のAPIキーを使う処理は追加しない。

### レビュー

- APIキーの直通GET /v1/modelsは200。実会話の08:25〜08:28の401は、LiteLLMがx-api-keyを上流へ転送する前に発生していた。forward_llm_provider_auth_headers:trueは維持されていたが、共有runtime-auth.jsonのx-litellm-api-keyが欠落していた。
- 残高機能の導入でbin/edualc-direct --versionを環境設定なしに実行したことにより、共通ファイルから接続ヘッダーが消えた。既に起動していたSDK側が後からファイルを再読込する経路だった。
- 同じBunプロセスを維持したまま別の起動で設定を変更する試験を追加した。修正前はキー・接続ヘッダー・ワークスペースがすべて変わり、修正後はすべて起動時の値を維持することを確認した。親のOAuthは保持し、SDKのOAuthは無効にする。
- 起動経路のヘッダーを共有runtime-authから除外し、各起動の環境から結合する。SDKの認証は初期化時に固定し、別の起動・検証・導入によるファイル上書きが実行中の会話へ影響しないようにした。native.25へ導入し、SDK 0.3.306を維持した。
- 実LiteLLM 1.102.0、ローカル模擬Anthropic上流、導入版TUIを使い、最初の起動後に別の起動でruntime-authを上書きしてから会話した。専用の使い捨てAPIキーが上流へ到達し、SDKの回答とstatuslineの残高が表示された。実際のAnthropic生成は呼んでいない。
- 認証4件、Bun117件、残高8件、型検査が成功。導入時に23接続モジュール・2428本家バイトコードの保持を照合した。証跡はevidence/authentication-file-isolation.jsonとtest/artifacts/credit-balance/installed-25-concurrent-auth.txt。既存の旧版会話用には欠落ヘッダーを一時復元したが、恒久修正を読み込むにはedualcの終了・再起動が必要。
